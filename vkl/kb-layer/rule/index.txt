15:T4778,<h2 id="definition">Definition</h2>
<p>In different cases we want to rewrite the VQL Veezoo generates from a user's question. We might want to add filters, change which function Veezoo uses in specific situations, correct potential errors, or insert our own definitions of concepts. With <code>Measures</code> and <code>default filters</code> Veezoo provides frameworks to rewrite VQL in a simple and straightforward fashion. <code>rules</code> are a more general method. They detect patterns in the generated VQL and modify them in a desired fashion.</p>
<p>For almost all cases there is a way to achieve the desired result using other tools than rules, in which case we strongly recommend to use the alternative instead: a <a href="/vkl/kb-layer/measure/">measure</a> for a KPI formula, a <a href="/vkl/kb-layer/class/default_filter/">default_filter</a> for a removable default. Reach for a rule only for what none of them can express.</p>
<aside class="docs-aside docs-aside--caution" data-title="Caution"><p class="docs-aside__title">Caution</p><p>Do not use rules as a security boundary. Restrictions like "West managers only see West rows" belong to <a href="/veezoo/authorization/row-level-permission/">Row-Level Permission</a>, where the restriction lives in the data access layer itself; a query rewrite is not a substitute for it.</p></aside>
<h2 id="structure">Structure</h2>
<p>Rules follow this structure:</p>
<figure class="docs-code"><pre class="shiki github-light" style="background-color:#fff;color:#24292e" tabindex="0"><code><span class="line"><span style="color:#24292E">rule only_show_active_customers {</span></span>
<span class="line"><span style="color:#6F42C1">    rule_pattern</span><span style="color:#24292E">:</span></span>
<span class="line"><span style="color:#032F62">        """</span></span>
<span class="line"><span style="color:#032F62">        // Matching Patter</span><span style="color:#B31D28;font-style:italic">n</span></span>
<span class="line"><span style="color:#D73A49">        var</span><span style="color:#24292E"> customer</span><span style="color:#D73A49">:</span><span style="color:#6F42C1"> kb</span><span style="color:#24292E">.</span><span style="color:#6F42C1">Customer</span></span>
<span class="line"></span>
<span class="line"><span style="color:#6A737D">        // Modification Pattern</span></span>
<span class="line"><span style="color:#24292E">        @add_if_not_exists {</span></span>
<span class="line"><span style="color:#24292E">            customer.is_active </span><span style="color:#D73A49">=</span><span style="color:#005CC5"> true</span></span>
<span class="line"><span style="color:#24292E">        }</span></span>
<span class="line"><span style="color:#032F62">        """</span></span>
<span class="line"><span style="color:#B31D28;font-style:italic">    </span></span>
<span class="line"><span style="color:#6A737D">    // specify which user role should have this logic applied</span></span>
<span class="line"><span style="color:#6F42C1">    for_user_role</span><span style="color:#24292E">: </span><span style="color:#032F62">"Marketing"</span></span>
<span class="line"><span style="color:#24292E">    </span></span>
<span class="line"><span style="color:#6A737D">    // specify the kind of rule</span></span>
<span class="line"><span style="color:#6F42C1">    rule_tag</span><span style="color:#24292E">: meta.SemanticLogicTag</span></span>
<span class="line"><span style="color:#24292E">    </span></span>
<span class="line"><span style="color:#6F42C1">    comment</span><span style="color:#24292E">: </span><span style="color:#032F62">"This is a description of the rule and its motivations."</span></span>
<span class="line"><span style="color:#24292E">}</span></span></code></pre></figure>
<h3 id="rule_pattern">rule_pattern</h3>
<p>The rule pattern consists of two parts: the <strong>Matching Pattern</strong> and the <strong>Modification Pattern</strong>.</p>
<p>The <strong>Matching Pattern</strong> can be a variety of VQL statements and serves two functions:</p>
<ul>
<li><em>Variable declaration</em>: <code>var customer: kb.Customers</code> declares the variable <code>customer</code>, which then can be referred to later on.</li>
<li><em>Rule condition</em>: Veezoo checks the <em>Matching Pattern</em> to see whether a rule should be applied. This rule comes into play only if everything listed in the <em>Matching Pattern</em> is also found in the VQL of the Question.</li>
</ul>
<p>Additionally we can use these functions to decide if the rule should be applied or not:</p>
<ul>
<li><code>@missing { ... }</code>:<br>
The rule should not be used, if the pattern in the brackets is present</li>
<li><code>{ ... } @or { ... }</code>:<br>
The rule should be applied when either pattern is present</li>
</ul>
<p>A common use of <code>@missing</code> is to stop a <code>@replace</code> rule from matching its own rewritten output: if the replacement still matches the rule's pattern, the rule would fire again on the rewritten query and the engine would abort. Guard the rule with an <code>@missing { ... }</code> on something that only appears in the rewritten form, so it fires exactly once per query.</p>
<p>The <strong>Modification Pattern</strong> defines the actual behavior of the rule. It takes its arguments from within its brackets. The following are the available <em>Modification Patterns</em>:</p>
<ul>
<li><code>@add_if_not_exists { ... }</code>:<br>
Adds a pattern to the VQL</li>
<li><code>@remove { ... }</code>:<br>
Removes a pattern from the VQL, if present</li>
<li><code>@remove_connected { ... }</code>:<br>
Similar to <em>@remove</em>, but also removes all classes connected to the pattern as well</li>
<li><code>@replace { ... } with { ... }</code>:<br>
Replaces a specific pattern with another</li>
</ul>
<h4 id="add_if_not_exists---">@add_if_not_exists { ... }</h4>
<p>This <em>Modification Pattern</em> is mostly used to add additional constraints or filters, the user didn't explicitly ask for, but we, as the data team, still want to be there. Let's look at the example given above again:</p>
<figure class="docs-code"><pre class="shiki github-light" style="background-color:#fff;color:#24292e" tabindex="0"><code><span class="line"><span style="color:#24292E">rule only_show_active_customers {</span></span>
<span class="line"><span style="color:#6F42C1">    rule_pattern</span><span style="color:#24292E">:</span></span>
<span class="line"><span style="color:#032F62">        """</span></span>
<span class="line"><span style="color:#032F62">        var customer: kb.Custome</span><span style="color:#B31D28;font-style:italic">r</span></span>
<span class="line"></span>
<span class="line"><span style="color:#24292E">        @add_if_not_exists {</span></span>
<span class="line"><span style="color:#24292E">            customer.is_active </span><span style="color:#D73A49">=</span><span style="color:#005CC5"> true</span></span>
<span class="line"><span style="color:#24292E">        }</span></span>
<span class="line"><span style="color:#032F62">        """</span></span>
<span class="line"></span>
<span class="line"><span style="color:#032F62">    for_user_role: "</span><span style="color:#24292E">Marketing</span><span style="color:#032F62">"</span><span style="color:#B31D28;font-style:italic"> </span></span>
<span class="line"><span style="color:#24292E">}</span></span></code></pre></figure>
<p>In this example, we want to ensure that users with the <code>user_role</code> <em>Marketing</em> can only see active customers.</p>
<ul>
<li>In the first line we define the variable <code>customer</code> and simultaneously state that this rule should be triggered if the pattern <code>kb.Customer</code> is present in the VQL.</li>
<li>We then use the <em>Modification Pattern</em>: if the filter <code>customer.is_active = true</code> is not present, we add it, such that all customers shown in the result are active.</li>
<li>We add the <code>for_user_role</code> such that this rule only applies to the marketing users (as explained later)</li>
</ul>
<p>A similar effect to this can be achieved by using <a href="/vkl/kb-layer/class/default_filter/">default filters</a>. There are two differences: default filters can be removed by business users, where as this rule will always be applied, and default filters can't be set for specific user roles.</p>
<h4 id="remove---">@remove { ... }</h4>
<p>With this <em>Modification Pattern</em> we can remove filters that Veezoo might add, but we don't want in certain cases.</p>
<p>Consider the following scenario: we have two datasets, <em>Employees</em> containing information about employees, including their status (active or inactive), and <em>Transactions</em> containing records of sales transactions, each associated with an employee. We want to calculate the total sales amount without filtering out inactive employees, as we need to consider sales made by all employees, regardless of their current status.</p>
<p>To this end, we use the following rule:</p>
<figure class="docs-code"><pre class="shiki github-light" style="background-color:#fff;color:#24292e" tabindex="0"><code><span class="line"><span style="color:#24292E">rule total_sales_all_employees {</span></span>
<span class="line"><span style="color:#6F42C1">    rule_pattern</span><span style="color:#24292E">:</span></span>
<span class="line"><span style="color:#032F62">        """</span></span>
<span class="line"><span style="color:#032F62">        var transactions: kb.Transaction</span><span style="color:#B31D28;font-style:italic">s</span></span>
<span class="line"><span style="color:#D73A49">        var</span><span style="color:#24292E"> employee</span><span style="color:#D73A49">:</span><span style="color:#6F42C1"> kb</span><span style="color:#24292E">.</span><span style="color:#6F42C1">Employee</span></span>
<span class="line"><span style="color:#6F42C1">        sum</span><span style="color:#24292E">(transactions.amount)</span></span>
<span class="line"><span style="color:#24292E">        transactions.with_Employee </span><span style="color:#D73A49">=</span><span style="color:#24292E"> employee</span></span>
<span class="line"><span style="color:#24292E">        @remove {</span></span>
<span class="line"><span style="color:#24292E">             # Remove the filter that only includes active employees</span></span>
<span class="line"><span style="color:#24292E">            employee.is_Active </span><span style="color:#D73A49">=</span><span style="color:#005CC5"> true</span></span>
<span class="line"><span style="color:#24292E">        }</span></span>
<span class="line"><span style="color:#032F62">        """</span></span>
<span class="line"><span style="color:#B31D28;font-style:italic">}</span></span></code></pre></figure>
<p>In the <em>Matching Pattern</em> we first define the variables <code>transactions</code> and <code>employee</code> and ensure that the rule is only applied when calculating the sum total of transactions. We specify that transactions is linked with employee using <code>transactions.with_Employee = employee</code>.</p>
<p>Using the <em>@remove</em> pattern, we then explicitly remove the filter that restricts the data to only active employees (<code>employee.is_Active = true</code>).</p>
<p>By applying this rule, we ensure that the total sales are calculated without excluding any employees based on their status. This way, sales made by inactive employees are also considered in the total, providing a complete picture of sales performance.</p>
<h4 id="replace----with---">@replace { ... } with { ... }</h4>
<p>This <em>Modification Patterns</em> is used to replace lines in VQL. A typical example of this is, when Veezoo would normally use a certain function, but we want to use a different one in a specific case. In the following example, we will show two uses of this rule pattern working together.</p>
<p>Consider the following situation. We have an <code>Orders</code> dataset where each order has an <code>Order_Qty</code> column. The <code>Order_Qty</code> values are adjusted based on business logic, such as 1 for regular orders, 0 for orders that shouldn't be counted, and -1 for orders that should decrease the count. This should be used when counting the orders instead of a <code>COUNT DISTINCT</code> on an order id.</p>
<p>This rule does this: it first checks if the question contains <code>kb.Orders</code>, and if so replaces all instances of the function <code>count(orders)</code> with <code>sum(orders.Order_Qty)</code>.</p>
<figure class="docs-code"><pre class="shiki github-light" style="background-color:#fff;color:#24292e" tabindex="0"><code><span class="line"><span style="color:#24292E">rule Substitute_Count_For_Sum {            </span></span>
<span class="line"><span style="color:#6F42C1">    rule_pattern</span><span style="color:#24292E">:</span></span>
<span class="line"><span style="color:#032F62">        """</span></span>
<span class="line"><span style="color:#032F62">        var orders: kb.Order</span><span style="color:#B31D28;font-style:italic">s</span></span>
<span class="line"><span style="color:#24292E">        @replace {</span></span>
<span class="line"><span style="color:#6F42C1">            count</span><span style="color:#24292E">(orders)</span></span>
<span class="line"><span style="color:#24292E">        } </span><span style="color:#D73A49">with</span><span style="color:#24292E"> {</span></span>
<span class="line"><span style="color:#6F42C1">            sum</span><span style="color:#24292E">(orders.Order_Qty)</span></span>
<span class="line"><span style="color:#24292E">        }</span></span>
<span class="line"><span style="color:#032F62">        """</span></span>
<span class="line"><span style="color:#B31D28;font-style:italic">}</span></span></code></pre></figure>
<p>In a next step, we would like to adapt the average function. Let's say we would like to figure out the average value of an order last month. The default average function might just calculate the average <code>Value</code> of all <code>Orders</code>. This, again, would be false. We therefore replace the default <code>average(orders.Value)</code> with <code>sum(orders.Value) / count(orders)</code>:</p>
<figure class="docs-code"><pre class="shiki github-light" style="background-color:#fff;color:#24292e" tabindex="0"><code><span class="line"><span style="color:#24292E">rule Adapt_Average {</span></span>
<span class="line"><span style="color:#6F42C1">    rule_pattern</span><span style="color:#24292E">:</span></span>
<span class="line"><span style="color:#032F62">        """</span></span>
<span class="line"><span style="color:#032F62">        var orders: kb.Order</span><span style="color:#B31D28;font-style:italic">s</span></span>
<span class="line"><span style="color:#24292E">        @replace {</span></span>
<span class="line"><span style="color:#6F42C1">            average</span><span style="color:#24292E">(orders.Value)</span></span>
<span class="line"><span style="color:#24292E">        } </span><span style="color:#D73A49">with</span><span style="color:#24292E"> {</span></span>
<span class="line"><span style="color:#6F42C1">            sum</span><span style="color:#24292E">(orders.Value) </span><span style="color:#D73A49">/</span><span style="color:#6F42C1"> count</span><span style="color:#24292E">(orders)</span></span>
<span class="line"><span style="color:#24292E">        }</span></span>
<span class="line"><span style="color:#032F62">        """</span></span>
<span class="line"><span style="color:#B31D28;font-style:italic">}</span></span></code></pre></figure>
<p>Note that this rule uses <code>count(orders)</code>. So, when asking <em>Average value of an order last month?</em>  Veezoo would first replace <code>average(orders.Value)</code> with <code>sum(orders.Value) / count(orders)</code>, and then in a second step this with <code>sum(orders.Value) / sum(orders.Order_Qty)</code>. If we would only ever be interested in the average, we could of course only have one rule do both.</p>
<h3 id="for_user_role-optional">for_user_role (optional)</h3>
<p>If there are user roles defined, you can use this tag to specify to whom the rule should apply. This can be useful, for example, if different roles have differing definitions of KPIs. For a more detailed explanation, see <a href="/veezoo/authorization/column-level-permission/#granting-column-level-permissions-with-for_user_role">here</a>.</p>
<h3 id="rule_tag-optional">rule_tag (optional)</h3>
<p>This tag specifies when the rule is applied. There are two options:</p>
<ul>
<li>use <code>meta.SemanticLogicTag</code> if the rule should be applied in the <em>Semantic Rewriting</em> stage</li>
<li>use <code>meta.LogicRewritingTag</code> if the rule should be applied in the <em>Logic Rewriting</em> stage</li>
</ul>
<h4 id="semantic-rewriting-stage">Semantic Rewriting stage</h4>
<p>This Rewriting stage is concerned with rewriting rules that need to be communicated to the user for clarity when answering.</p>
<p>Classical examples are default values, e.g. "how many customers" means "how many active customers" by default and the user should be made aware of that, in case that's not what he/she wants.</p>
<h4 id="logic-rewriting-stage">Logic Rewriting stage</h4>
<p>In contrast to Semantic Rewriting, rules in Logic Rewriting are rather technical and have no meaning for the end user.</p>
<p>A common case is when the database does not have the sought concept raw stored, but it should be computed from other concepts. We call these higher-order concepts.</p>
<p>These are usually KPI definitions (<code>measure</code>), e.g. to compute the profit we need to add <em>revenue x</em> with <em>revenue y</em> and subtract <em>costs z</em>, but not <em>costs w</em>.</p>
<p>The main difference for users will be if the rule affects the title of answers or not. If no <code>rule_tag</code> is specified, <code>meta.SemanticLogicTag</code> will be used by default.</p>
