15:T28d7,<p>When using single sign-on with SAML or JWT, you can define some attributes of users in Veezoo based on values from the authentication token:</p>
<ul>
<li>when using SAML: based on attributes from the SAML assertion</li>
<li>when using JWT: based on claims from the JWT</li>
</ul>
<h2 id="attributes">Attributes</h2>
<p>The following attributes can be configured:</p>













































<table><thead><tr><th>Attribute</th><th>Description</th><th>Multi-valued</th></tr></thead><tbody><tr><td><strong>Tenant</strong></td><td>The tenant the user belongs to (only available when using multi-tenancy)</td><td>no</td></tr><tr><td><strong>Type</strong></td><td>The user's type (<code>Viewer</code>, <code>Creator</code>, or <code>Admin</code>). A mapping is <strong>required</strong> - see the note below.</td><td>no</td></tr><tr><td><strong>First name</strong></td><td>The user's first name</td><td>no</td></tr><tr><td><strong>Last name</strong></td><td>The user's last name</td><td>no</td></tr><tr><td><strong>E-mail</strong></td><td>The user's e-mail address</td><td>no</td></tr><tr><td><strong>Language</strong></td><td>The user's preferred language, if supported by a given knowledge graph</td><td>no</td></tr><tr><td><strong>Roles</strong></td><td>The user's roles</td><td>yes</td></tr></tbody></table>
<aside class="docs-aside docs-aside--caution" data-title="A Type mapping is required"><p class="docs-aside__title">A Type mapping is required</p><p>The <strong>Type</strong> attribute determines the <a href="/veezoo/authorization/viewer-creator-users">type</a> a user is created with, and it has no default. If <strong>no</strong> Type mapping matches, the user is created <strong>deactivated</strong> and cannot sign in - the authentication request fails with <code>401 Unauthorized</code> and the message <code>User is deactivated</code>.</p><p>This applies to <strong>every</strong> sign-in, not just the first one: the mappings are re-evaluated and the user's type is refreshed on each authentication. Activating such a user manually therefore has no lasting effect - the next sign-in deactivates them again. The fix is always at the mapping level: the user can sign in as soon as <strong>at least one</strong> Type mapping matches, whether you add a mapping, adjust an existing one, or correct the value sent in the token.</p></aside>
<p>To be safe, make the <strong>last</strong> Type mapping an unconditional one. It acts as a catch-all, so a user whose token carries an unexpected or missing value still gets a type assigned instead of being locked out:</p>





















<table><thead><tr><th>Value</th><th>Condition</th></tr></thead><tbody><tr><td><code>Admin</code></td><td><code>type == 'Admin'</code></td></tr><tr><td><code>Creator</code></td><td><code>type == 'Creator'</code></td></tr><tr><td><code>Viewer</code></td><td><em>(none)</em></td></tr></tbody></table>
<h2 id="mapping">Mapping</h2>
<p>For each user attribute, you can define one or more mappings that determine the value of the attribute. When a user authenticates, i.e. opens or reloads Veezoo in their browser, the mappings are evaluated and the corresponding user attributes are <strong>updated</strong> accordingly.</p>
<p>Mappings are evaluated in order from top to bottom:</p>
<ul>
<li>for <strong>single-valued</strong> user attributes, the <strong>first matching mapping</strong> is used</li>
<li>for <strong>multi-valued</strong> user attributes, <strong>all matching mappings</strong> are applied.</li>
</ul>
<p>Each mapping consists of the following fields:</p>
<p><img src="/img/single-sign-on/saml/user-attribute-mapping.png" alt="User attribute mapping"></p>
<h3 id="value">Value</h3>
<p>The value to assign to the user attribute, if the condition holds.</p>
<p>For some user attributes (e.g. type), the permitted values are predefined and can be selected using a dropdown. For other attributes (e.g. first name), the entered value must be a <a href="#variable">variable</a> or a <a href="#string">string</a>.</p>
<h3 id="condition">Condition</h3>
<p>The condition which determines if the mapping should be used <em>(optional)</em>.</p>
<p>If set, then the mapping's value is only assigned to the user attribute if the condition holds, else the mapping is ignored. The entered value must be a <a href="#condition-1">condition</a>.</p>
<h3 id="description">Description</h3>
<p>The description for the mapping <em>(optional)</em>.</p>
<h2 id="syntax">Syntax</h2>
<p>The following simple syntax can be used to express conditions and reference attributes from the authentication token (i.e. SAML assertion attributes or JWT claims).</p>
<h3 id="string">String</h3>
<p>A string is enclosed in single quotes.</p>
<p><strong>Example:</strong> <code>'abc'</code></p>
<h3 id="array">Array</h3>
<p>An array encloses a comma-separated list of strings in brackets.</p>
<p><strong>Example:</strong> <code>['a', 'b', 'c']</code></p>
<h3 id="variable">Variable</h3>
<p>A variable references an attribute from the authentication token, i.e. a SAML assertion attribute or JWT claim).</p>
<p>If the variable contains non-alphanumerical characters, then it needs to be enclosed in backticks.</p>
<p><strong>Examples:</strong></p>
<ul>
<li><code>firstName</code></li>
<li><code>`first-name`</code></li>
<li><code>`http://schemas.xmlsoap.org/ws/2005/05/identity/claims/givenname`</code></li>
</ul>
<h3 id="condition-1">Condition</h3>
<p>A condition consists of a left-hand side, an operator and a right-hand side.</p>













































<table><thead><tr><th>Operator</th><th>Name</th><th>Description</th></tr></thead><tbody><tr><td><code>==</code></td><td>Equality</td><td>Evaluates to true if the left-hand side is equal to the right-hand side</td></tr><tr><td><code>!=</code></td><td>Non-equality</td><td>Evaluates to true if the left-hand side is not equal to the right-hand side</td></tr><tr><td><code>IN</code></td><td>Containment</td><td>Evaluates to true if the left-hand side is contained in the right-hand side</td></tr><tr><td><code>NOT IN</code></td><td>Non-containment</td><td>Evaluates to true if the left-hand side is not contained in the right-hand side</td></tr><tr><td><code>AND</code> / <code>&#x26;&#x26;</code></td><td>Conjunction</td><td>Evaluates to true if both the left-hand side and right-hand side evaluate to true</td></tr><tr><td><code>OR</code> / <code>|</code></td><td>Disjunction</td><td>Evaluates to true if either of the left-hand side and right-hand side evaluate to true</td></tr><tr><td><code>NO</code> / <code>!</code></td><td>Negation</td><td>Negates the result of the condition</td></tr></tbody></table>
<p><strong>Examples:</strong></p>
<ul>
<li>Equality:<br>
<code>language == 'fr'</code><br>
<code>departmentCodes == ['D1', 'D2']</code></li>
<li>Non-equality:<br>
<code>language != 'fr'</code><br>
<code>departmentCodes != ['D1', 'D2']</code></li>
<li>Containment:<br>
<code>departmentCode IN ['D1', 'D2', 'D3']</code><br>
<code>'D1' IN departmentCodes</code></li>
<li>Non-containment:<br>
<code>departmentCode NOT IN ['D1', 'D2', 'D3']</code><br>
<code>'D1' NOT IN departmentCodes</code></li>
<li>Conjunction:<br>
<code>language == 'fr' &#x26;&#x26; departmentCode IN ['D1', 'D2', 'D3']</code></li>
<li>Disjunction:<br>
<code>language == 'fr' || departmentCode IN ['D1', 'D2', 'D3']</code></li>
<li>Negation:<br>
<code>NOT language == 'fr'</code><br>
<code>! language == 'fr'</code></li>
<li>Parentheses:<br>
<code>!(language == 'fr')</code><br>
<code>((a == '1' OR a == '2') AND NOT(b == '3'))</code></li>
</ul>
<aside class="docs-aside docs-aside--note" data-title="Note"><p class="docs-aside__title">Note</p><ul>
<li>A string is considered to be equal to an array holding exactly that string
E.g. <code>'a' == ['a']</code> holds true</li>
<li>The left-hand side of a (non-)containment condition can be an array
E.g. <code>['b', 'a'] IN ['a', 'b', 'c']</code> holds true</li>
</ul></aside>
